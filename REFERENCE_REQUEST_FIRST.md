## P0 request flow (single source of truth)
1. Authenticate workspace and request; reject malformed or over-limit requests.
2. Read complete Anthropic messages request including system prompt, tool schemas, history, user message, model, and max_tokens. Redact/avoid storing raw PII.
3. Estimate input tokens from complete serialized text, initially chars/4 for English, mark as approximate. Prefer local tokenizer if validated. Record method, language, and estimate. Token counting endpoints, if used, add latency and should be measured separately; do not imply characters/4 is exact.
4. Predict output tokens BEFORE provider call from a trained regression using past request metadata (input token estimate, requested model, max_tokens, task/FAQ category, and optional rolling history). Clip prediction to [0, max_tokens]. Short prompts requesting long reports require task intent/length features; otherwise the model may underestimate. Report uncertainty/error; never guarantee output size.
5. Estimate request cost using versioned pricing and explicit MYR/USD FX assumptions; cache read tokens, provider prompt caching, and tools may require distinct price terms. Calculate estimated ceiling using max_tokens, clearly separate from expected cost.
6. Evaluate action **before** provider call, in this priority: approved safe FAQ cache hit; approved, quality-tested routing for allowlisted simple tasks (P1); approved, semantics-preserving output cap for allowlisted tasks (P1); otherwise pass through unchanged. Cache misses always preserve the requested model by default. No automatic throttling in P0.
7. Call Anthropic only for uncached requests. Capture actual input/output tokens and provider-reported cache usage; compute actual spend using pricing effective at call time.
8. Persist one immutable event with prediction, actual usage/cost, action, requested/used model, cache status, provenance, approval policy ID, and prediction error. Cache hits record provider_cost=0 but can have nonzero local overhead.
9. Aggregate events to dashboard; update month-end forecast and anomaly detection; run what-if simulations against the SAME forecast and recommend only approved/tested actions.
10. Compare predicted vs actual costs and intervention quality; display real, synthetic, and estimated numbers with different labels.

## Request prediction model
P0 baseline: rolling median output tokens per `(model, task_category, input_size_bucket)` with global fallback, clipped to max_tokens. P0 trained model: scikit-learn HistGradientBoostingRegressor or Ridge/OneHotEncoder pipeline with features available before inference. Select trained model ONLY if its chronological held-out MAE improves over baseline; otherwise ship baseline and clearly show comparison. For a 24-hour build, a small Ridge model is acceptable if data is sufficient. Evaluate output-token MAE, median absolute error, P90 absolute error, and cost MAE; break down by short/long requests and model. Split by timestamp, no leakage from future usage, synthetic history separate from real test. A model trained solely on synthetic data cannot establish real-world accuracy.

## Dataset and anomaly generation
Produce deterministic synthetic 180-day history (seed=42) with weekday/weekend seasonality, model mix, request categories, varying input and output lengths, cacheable FAQs, provider pricing versions, and genuine request-level records or realistic aggregated sampling. Inject annotated anomalies: (a) 4x traffic burst, (b) output-token explosion from long-report prompts, (c) sudden shift to expensive model, (d) retry loop causing duplicate calls, (e) elevated error rate, (f) low cache-hit rate despite repeatable queries, (g) gradual traffic drift, (h) one-off promotion that should not trigger a severe alert. Preserve clean anomaly labels. Include train/validation/test time windows and prevent leakage from injected future labels. Use IsolationForest plus robust rolling median/MAD; report precision, recall, F1, false positives per 30 days, and detection delay. Evaluate thresholds only on validation set, then freeze for test. A synthetic evaluation must be labelled synthetic.

## Safe caching
P0 only deterministic, approved, versioned bakery FAQ answers. Exact canonical FAQ match first. Optional local embedding similarity >=0.95 is only a candidate gate; require same tenant, locale, FAQ intent ID, knowledge-base version, approved answer version, TTL, and absence of personal/order/status/time-sensitive requests. Do not cache free-form conversations or arbitrary Claude responses merely because embeddings match. Store FAQ fingerprints and expiry; invalidate on knowledge-base changes. Record cache hits with provider_cost=0; quantify local lookup overhead. Add adversarial tests: 'what time do you open' vs 'what time does my order arrive', negation, refund exceptions, different tenant, outdated prices, languages, personally identifying text.

## Routing and trimming
Both OFF by default. Owner must approve; additionally routing must pass a 20-prompt paired quality test with a published pass/fail rubric before being marked LIVE. Validate actual Anthropic model IDs from the provider configuration, do not assume `claude-haiku-5-5` exists. Routing may not silently downgrade, and must expose requested/used model. Trimming is only a per-request max_tokens policy for explicitly approved short-response FAQ categories; never truncate requested long-form reports. Return visible action metadata; do not rely exclusively on response headers for browser UIs. Mark automatic throttling NEXT.
